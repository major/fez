## What this is

`fez` is an agent-native management CLI for Fedora/RHEL. It drives
`cockpit-bridge` over its framed JSON protocol (spawns the bridge, opens
channels, delegates privilege escalation to it) and reaches remote hosts by
shelling out to the system OpenSSH client. Rust, edition 2021, MSRV **1.92**
(pinned in `rust-toolchain.toml` and `Cargo.toml`; keep both in sync on bump).

Crates.io package name is `rusty-fez` because `fez` is already taken. The
installed binary and library crate name stay `fez`.

**fez holds no state.** It never writes a state file, cache, lock, or
spool (no `/var/lib/fez`, no `XDG_STATE_HOME`, no temp snapshots). Every
invocation is self-contained: it reads live system state through the bridge,
acts, emits the envelope, and exits. The source of truth always lives in the
managed subsystem (systemd, dnf5daemon, NetworkManager, firewalld), never in
fez. When a feature seems to need memory across invocations, push that state
into the subsystem (e.g. firewalld's own runtime-vs-permanent split and
`runtimeToPermanent`) or recompute it on each call, rather than persisting it
in fez. The only thing fez writes is the append-only audit log, and that is a
sink, not state fez ever reads back.

## Commands

Use the Makefile, not raw cargo, for gated work. `make` defaults to `check`.

- `make check` - local one-shot gate: `lint test docs-coverage security`
- `make lint` - `cargo fmt --check` then `cargo clippy --all-targets -- -D warnings`
- `make test` - `cargo test` (unit + integration)
- `make coverage` / `make coverage-html` - lcov for Codecov / HTML report
- `make docs-coverage` - **requires the nightly toolchain** (`cargo +nightly`); enforces 100% docstring coverage via `scripts/docs_coverage.py`
- `make security` - supply-chain + dep hygiene: `deny machete`
  - `make deny` - `cargo deny check` (RUSTSEC advisories, license policy, banned/duplicate crates, source allow-list; config in `deny.toml`). Install: `cargo install cargo-deny --locked`
  - `make machete` - `cargo machete` (unused declared deps). Install: `cargo install cargo-machete --locked`
- `make msrv` - `cargo +1.92 check --all-targets`; proves the crate compiles on the pinned MSRV, not just stable. Requires `rustup toolchain install 1.92`
- Single test: `cargo test --test services name_of_test` (integration files are `tests/cli.rs`, `tests/mcp.rs`, `tests/packages.rs`, `tests/services.rs`, `tests/network.rs`)

## Architecture

Thin binaries over a library (`src/lib.rs` owns the module tree; `run()` is the single entry point). Key modules:

- `protocol/` - wire protocol to the bridge: `frame` (framed JSON), `message` (incl. `DbusSignal`, the signal-frame parse type), `client` (`dbus_call` for request/reply, `dbus_call_collect` for the signal-driven PackageKit path)
- `transport/` - `local` (spawns the bridge) and `ssh` (OpenSSH client) ways to reach it
- `capabilities/` - the actual commands fez runs (e.g. `services`, `packages`, `network`, `firewall`); `capability/` holds machine-readable descriptors of that surface. `packages` drives dnf5daemon and falls back to `packages_pk` (the PackageKit backend) when dnf5daemon is absent
- `dispatch.rs` - routes parsed CLI to capabilities (private module)
- `cli.rs` - clap definitions plus `command()` (the registry-enriched command tree), `raw_command()` (the bare derived tree), and `parse_or_render()` (the binary entry point: it `try_get_matches`-es, renders `--help`/`--version` itself, and on a clap **usage** error honors `--json` by emitting a `fez/v1` error envelope (code `usage`, exit 2) on stdout instead of clap's stderr text, issue #52). New top-level verbs beyond the capability commands: `fez guide` (agent contract; `--json` emits an `AgentGuide` envelope), `fez completions <shell>` (bash/zsh/fish), and hidden `fez man` (emits the `fez.1` roff page; packaging runs it during `%build`). `envelope.rs` - the `fez/v1` JSON response envelope
- `safety.rs` - guardrails: protected units refuse mutation without `--force`
- `audit.rs` - JSON-lines audit log of attempted + completed mutations (each executed mutation writes two records: attempt + result)
- `mcp/` - MCP server (`fez mcp`, JSON-RPC 2.0 over stdio). A server launched with global `--host <host>` uses that resolved host as the default target for `invoke` calls that omit `arguments.host`; a per-call `arguments.host` still overrides it. The default target is exposed in `initialize.serverInfo.defaultTargetHost` and the `invoke` tool description from `tools/list`.

Errors: single `FezError` enum (`src/error.rs`) with stable string `code()` and `exit_code()` mappings. Exit codes are part of the contract (e.g. usage = 2, not-found = 4, protected-unit = 8, timeout = 5, bridge spawn/closed = 6, dbus = 7, dependency-missing = 9, dangerous-transaction = 10, access-denied = 11). The `usage` code (exit 2, matching clap's convention) covers CLI parse failures rendered as JSON; clap surfaces these before a `FezError` exists, so `parse_or_render()` builds the envelope directly while `FezError::Usage` carries the same code/exit for the table and tests. E2E and integration tests assert on them; update tests when you touch the mapping.

## Testing quirks

- Shared integration scaffolding lives in `tests/common/mod.rs` (pulled in per suite via `mod common;`). It exports `fez_fake()` (command wired to the fake bridge), `fez_fake_quiet()` (same plus `FEZ_AUDIT=off`, used by `firewall.rs` via a `use ... as fez_fake` alias), `fez_plain()` (no bridge, for `cli.rs` CLI-surface tests), the `PKG_COLUMNS` `PackageList` header constant, and an RAII `AuditLog` guard (`new(label)` / `env_value()` / `records()`; removes its temp file on drop) used by the `services`/`packages` audit-record tests. Suite-specific helpers stay local (e.g. `fez_without_bridge`/`fake_transport` in `services.rs`, `fez_mcp` in `mcp.rs`, which wraps `fez_fake().arg("mcp")`). `common` also exports `fez_fake_pk()` (`fez_fake_quiet()` plus `FEZ_FAKE_NO_DNF5`) used by `packages_pk.rs` to exercise the PackageKit fallback. The `common/` subdir is a module dir, not its own test binary, so the suite count is **11** (`cli`, `mcp`, `packages`, `packages_pk`, `services`, `network`, `firewall`, and the rest).
- Integration tests drive a **fake bridge binary** (`src/bin/fake_bridge.rs`, built as `fez-fake-bridge`) instead of a real `cockpit-bridge`. Tests point fez at it via the `FEZ_BRIDGE` env var set to `env!("CARGO_BIN_EXE_fez-fake-bridge")`. The fake reports `chronyd` inactive and `sshd` active; assertions depend on that.
- Packages integration tests (`tests/packages.rs`) drive the same fake bridge over `org.rpm.dnf.v0` (dnf5daemon). `FEZ_FAKE_PLAN` selects the staged transaction plan the fake returns from `Goal.resolve` (`install`/`small`/`protected`/`cascade`, exercising the removal guardrails); `FEZ_FAKE_NO_DNF5` makes the fake report the daemon absent (`ServiceUnknown`) to exercise the exit-9 `dependency-missing` path. The fake's `Rpm.list` returns a fixed multi-repo set (`bash`/`htop`/`nginx` from `fedora`, `vim-enhanced` from `updates`) so the `--repo` filter is testable. dnf5daemon's `Rpm.list` has **no** server-side repo filter (only `install`/`upgrade` take `repo_ids`, for resolution), so `packages list --repo` filters client-side on the exact `repo_id`; multiple `--repo` flags union, and the applied filter is echoed in the envelope's `repos` field (issue #59).
- PackageKit fallback integration tests (`tests/packages_pk.rs`) drive the same fake bridge over `org.freedesktop.PackageKit`, with `FEZ_FAKE_NO_DNF5` set (via `fez_fake_pk()`) so the dnf5daemon `open_session` returns `ServiceUnknown` and `packages` falls back to PackageKit. PackageKit is **signal-driven**, not request/reply: a `CreateTransaction` call returns a canned transaction object path as a normal reply, then transaction methods (`GetPackages`/`GetUpdates`/`SearchNames`/`GetRepoList`/`Resolve`/`InstallPackages`/`UpdatePackages`/`RemovePackages`) emit `{"signal":[path, iface, member, args]}` data frames (`Package`/`RepoDetail`/`ErrorCode`) terminated by a `Finished` signal. The client collects these via `BridgeClient::dbus_call_collect` (the request/reply `dbus_call` never sees them). The fake's `pk_emit` produces the canned stream; the dispatch loop routes `CreateTransaction` on `/org/freedesktop/PackageKit` and any call on the transaction path (`/org/freedesktop/PackageKit/Transaction/1`) **before** the dnf arm. Knobs: `FEZ_FAKE_NO_PACKAGEKIT` makes `CreateTransaction` return `ServiceUnknown` (model PackageKit absent, so the **both-backends-absent** path returns exit 9 naming both daemons); `FEZ_FAKE_PK_PLAN=protected` adds `systemd` to the `RemovePackages` plan so the removal guardrail refuses the dangerous transaction (exit **10**, `dangerous-transaction`, not 8); `FEZ_FAKE_PK_ERROR=notauth` emits `ErrorCode(6, ...)` (`PK_ERROR_ENUM_NOT_AUTHORIZED`) which the backend maps to exit 11 (`access-denied`). PackageKit payloads carry `"backend":"packagekit"`, set `install_size`/`install_size_total` to `null` (PackageKit's plan has no sizes), and carry a degraded-schema hint; dnf5daemon payloads now carry `"backend":"dnf5daemon"` for symmetry. Reads run unprivileged; mutations open a privileged channel (root-via-cockpit bypasses PackageKit's `auth_admin` polkit actions), so a no-escalation host (`FEZ_FAKE_BRIDGES=""`) fails a mutation with exit 11.
- The fake bridge models **transparent escalation** over `cockpit.Superuser`. fez sends `init` with `superuser: "none"` (deferring escalation), so the fake just completes the handshake with its own `init` reply and **no** `superuser-init-done` (real cockpit only runs superuser negotiation, and only then fires `superuser-init-done`, when init carries an escalation request; a bare `superuser: "none"` never triggers it). The client treats the bridge `init` as handshake-complete and does not wait for `superuser-init-done` (waiting for it hangs against a real bridge). Escalation is driven later by the client: it reads the `cockpit.Superuser` `Bridges` property and calls `Start(name)` over the internal bus (`bus: "internal"`, object path `/superuser`, interface `cockpit.Superuser`) until one mechanism succeeds. The `Bridges` read goes through `Properties.Get`, whose single out-arg is a D-Bus variant, so the `as` value is variant-wrapped (`{"t":"as","v":[...]}`); the fake wraps it and the client unwraps via `variant_value` before iterating mechanisms. A fake that returned the bare array would mask a client that fails to unwrap and would silently see zero mechanisms (spurious exit 11). `FEZ_FAKE_BRIDGES` configures the fake's advertised mechanisms as an ordered `name:outcome` list (`sudo:ok`, `sudo:err,polkit:ok`, ...); a bare `name` defaults to `ok`. Unset defaults to a passwordless-sudo host (`sudo:ok`), so most tests escalate without ceremony; an explicitly empty value (`FEZ_FAKE_BRIDGES=""`) advertises no mechanism, so privileged channels are denied (exit 11). `FEZ_FAKE_DENY_PRIVILEGED` models a host where escalation succeeds but the policy still rejects the privileged channel mid-operation (the bridge closes it `access-denied` even after a successful `Start`). Real standalone `cockpit-bridge` (no `cockpit-system`) advertises **zero** superuser bridges, so privileged channels are denied; escalation requires `cockpit-system` (it ships the sudo/pkexec bridge definitions) plus either passwordless sudo or a polkit rule. fez does not supply sudo passwords. The runtime `FEZ_ESCALATION` knob overrides mechanism selection: `off` disables escalation, any other value forces that single mechanism with no fall-through.
- The fake bridge **rejects `a{sv}` option dicts whose values are not variant-wrapped** (`reject_unwrapped_options`), mirroring real cockpit-bridge: every value of an `a{sv}` argument must be `{"t":<sig>,"v":<value>}`, not a bare scalar, or the bridge raises a marshalling `TypeError`. dnf option dicts are built via the `options()`/`variant()` helpers in `capabilities/packages.rs` so this stays correct. If you add a dnf method that takes an options dict, route it through those helpers or the integration tests will fail with `InvalidArgs`.
- Network integration tests (`tests/network.rs`) drive the same fake bridge over `org.freedesktop.NetworkManager`. NM reuses the generic `Get`/`GetAll` property methods across many object types, so the fake's `nm_reply` dispatches by **object path** (manager, `Devices/<n>`, `IP4Config/<n>`, `IP6Config/<n>`, `ActiveConnection/<n>`, `DHCP4Config/<n>`), not by method name like the systemd/dnf surfaces; the dispatch loop routes any call whose path starts with `/org/freedesktop/NetworkManager` to it first. Canned topology from `GetDevices`: `enp1s0` (ethernet, activated, full IPv4/IPv6/active-conn/DHCP), `enp2s0` (ethernet, unavailable, null `"/"` IP configs to exercise the absent-config guard), `lo` (loopback, unmanaged but kept by the default type filter), and `veth0` (veth, unmanaged, hidden by default and shown only with `--all`). Every `a{sv}`/variant value is variant-wrapped (`{"t":<sig>,"v":<value>}`) like the systemd `GetAll` arm. The `network` capability is read-only (unprivileged `dbus_open`, no escalation). `network list` hides unmanaged virtual interfaces unless `--all`; `network show <device>` looks the device up by `Interface` name and returns exit 4 (`not-found`) for an unknown name.
- Firewall integration tests (`tests/firewall.rs`) drive the same fake bridge over `org.fedoraproject.FirewallD1`. The fake's `fw_reply` dispatches by object path **and interface**, mirroring real firewalld: the firewalld surface is split across interfaces, so a method called on the wrong interface yields `UnknownMethod`. This matters because `getZones`/`getServices`/`getPorts`/`getInterfaces`/`getSources` live on the **zone** interface (`org.fedoraproject.FirewallD1.zone`), while `getDefaultZone`/`listServices`/`queryPanicMode` and the mutations live on the **root** interface (`org.fedoraproject.FirewallD1`). A path-only fake that ignored the interface masked a real bug where fez called `getZones` on the root interface (issue #33); the interface-aware fake reproduces it. The permanent **config** interface (`config`/`config.zone`) is polkit-gated (firewalld's `PK_ACTION_CONFIG`/`config.info`, `auth_admin_keep` on both server and desktop installs), so the fake answers config reads **only on a privileged channel** and otherwise returns an `AccessDenied` D-Bus error; the fake tracks which channels were opened `superuser: "require"` in a `privileged_channels` set. fez therefore reads permanent config for drift over a privileged (escalated) channel, even in the otherwise-unprivileged `status` (issue #34). Canned topology: default zone `public`; zones `public`/`internal`/`drop`; runtime `public` carries `ssh`/`dhcpv6-client` services and `9090/tcp`, while permanent `public` lacks `9090/tcp`, so runtime-vs-permanent drift is non-empty out of the box (`status` reports `+port 9090/tcp`, and `confirm` has something to commit). Runtime `public` masquerade is also seeded on while permanent is off, so `status` likewise reports `+masquerade`. Runtime reads are unprivileged; the permanent-config read and all mutations escalate via the existing `FEZ_FAKE_BRIDGES` machinery (an empty value yields exit 11 on a mutating call **and on `status`**, since status now escalates for the permanent read). The firewall methods used take plain typed args, not `a{sv}` option dicts, so they need no variant wrapping in either direction. Test-only knobs: `FEZ_FAKE_NO_FIREWALLD` (the FirewallD1 service reports absent -> exit 9), `FEZ_FAKE_PANIC` (start in panic-on state), and `FEZ_FAKE_PORT_REMOVED` (drop `9090/tcp` from the runtime `public` zone, modeling the post-`remove-port` read). The protected-op guard (removing the session ssh service/port, any default-zone change, `panic on`, and a drift-discarding `reload`) refuses without `--force` (exit 8); session-criticality is derived live from `$SSH_CONNECTION` (server port) with `ssh` always treated as critical.apping in either direction. Test-only knobs: `FEZ_FAKE_NO_FIREWALLD` (the FirewallD1 service reports absent -> exit 9) and `FEZ_FAKE_PANIC` (start in panic-on state). The protected-op guard (removing the session ssh service/port, any default-zone change, `panic on`, and a drift-discarding `reload`) refuses without `--force` (exit 8); session-criticality is derived live from `$SSH_CONNECTION` (server port) with `ssh` always treated as critical.
- `FEZ_FAKE_CONFIG_INFO_DENIED=1` models the real-host firewall case where cockpit opens a privileged channel, but firewalld still rejects the permanent `config.info` polkit action. `firewall status` treats that as a partial read: it returns runtime status with `pending_changes_available:false`, an empty `pending_changes` list, and a hint that permanent config was not readable. Keep `FEZ_FAKE_BRIDGES=""` for the separate no-escalation case, which still exits 11 before any permanent read can run.
- Envelope JSON is **compact** (`Envelope::to_json_string` uses `serde_json::to_string`, no spaces). Assert `--json` output with substrings like `"kind":"ServiceList"` (no space after the colon). Pretty-printed `"kind": "X"` passes against a stale local build but fails in CI's clean build.
- E2E (`test/e2e/run.sh`) provisions real cloud hosts via Terraform, installs `cockpit-bridge` + backends, and exercises the real transport across the **OS matrix** (Fedora + RHEL 10 by default; override with `FEZ_E2E_OS="fedora rhel10"`). Expensive and destructive (auto-`destroy` on exit). The harness is **phased**, not fan-out: (1) `lib/provision.sh` does **one** `terraform apply` over `var.oses` (a `set(string)`; `aws_instance.e2e` uses `for_each`, so Terraform's DAG parallelizes the per-OS instances). Terraform owns the readiness wait via a per-host `remote-exec` provisioner that blocks on `/var/lib/fez-e2e-ready` with a hard timeout (`var.ready_timeout_seconds`, default 300); a host that never readies taints **only its own** instance, the apply exits non-zero, and the runner tolerates that and derives survivors from `terraform output -json` (per-OS maps: `public_ips`/`ssh_users`/`ami_names`). (2) The test phase loops over `READY_OSES`, sets per-host context (`OS`, `FEZ_SSH_CONFIG`, `WORK`, `STEP_LOG`) and runs every `test_<cap>` in `lib/capabilities.sh` against each survivor, recording `os cap status` triples in `RESULT_FILE` for the matrix table. (3) `lib/teardown.sh` is wired to a single `EXIT` trap that destroys the one shared Terraform stack (including tainted hosts) on success, failure, or Ctrl-C, so no instance leaks. Failures are **never auto-filed as issues**: each failing cell's forensics are echoed inline to the matrix log (file tickets by hand). The bounded SSH config (`ConnectTimeout`/`ServerAlive*`) prevents any one-shot probe from wedging the run (issue #49). It auto-`tee`s every run to `test/e2e/logs/matrix-<ts>.log` (gitignored) with a `last-run.log` symlink; read the log on failure. It pins SSH config with `FEZ_SSH_CONFIG` (`ssh -F`), not `HOME`, because OpenSSH ignores `$HOME/.ssh/config` non-interactively. A preflight `aws sts get-caller-identity` fails fast (exit 2) if no AWS credentials resolve, instead of burning the IMDS timeout.
- E2E provisioning (`test/e2e/terraform/user_data.sh`) installs a hard-required core (`cockpit-bridge cockpit-system firewalld`, always present, abort+fail the host if it fails) plus the **optional, OS-dependent** `dnf5daemon-server`. The package backend is gated by a `with_dnf5daemon` template bool that `main.tf` sets from `each.key` (`!= "rhel10"`): on Fedora the package is appended to the single `dnf install` argv (so a genuine install failure still aborts and surfaces a real fault), on RHEL 10 it is simply omitted from the argv, because RHEL 10 is a dnf4 stack and the package does not exist in BaseOS/AppStream/CRB (issue #50). Omitting it (rather than installing best-effort and swallowing the error) means dnf is never asked for a nonexistent package, so `set -e` has nothing to trip over. On RHEL 10 the host still readies and runs services/network/firewall; `test_packages` in `lib/capabilities.sh` sees fez exit 9 and records `skip` (the matrix counts only `fail` cells, so a RHEL 10 `packages skip` is green).

## Env vars

Runtime knobs read from the environment: `FEZ_BRIDGE` (bridge binary path, used by tests), `FEZ_AUDIT` (audit sink, e.g. `file:/path/audit.jsonl`), `FEZ_SSH_CONFIG` (ssh `-F` config), `FEZ_ESCALATION` (privilege-escalation override: `off` disables escalation, any other value forces that single mechanism instead of the default sudo-then-polkit fall-through). Audit records also carry `FEZ_ACTOR`, `FEZ_CORRELATION_ID`, `FEZ_TARGET_HOST`, `FEZ_OPERATION`, `FEZ_UNIT`, etc. Test-only fake-bridge knobs: `FEZ_FAKE_PLAN` (selects the canned dnf5daemon `Goal.resolve` plan: `install`/`small`/`protected`/`cascade`), `FEZ_FAKE_NO_DNF5` (simulates dnf5daemon being absent), `FEZ_FAKE_BRIDGES` (ordered `name:outcome` list of advertised `cockpit.Superuser` mechanisms; unset defaults to `sudo:ok`, empty advertises none), `FEZ_FAKE_DENY_PRIVILEGED` (deny the privileged channel even after a successful `Start`), `FEZ_FAKE_NO_FIREWALLD` (simulates firewalld being absent), `FEZ_FAKE_PANIC` (start the fake firewall in panic-on state), `FEZ_FAKE_PORT_REMOVED` (drop the drift port `9090/tcp` from the runtime `public` zone, modeling the state after a `remove-port`), `FEZ_FAKE_CONFIG_INFO_DENIED` (deny permanent firewalld `config.info` reads after escalation), `FEZ_FAKE_NO_PACKAGEKIT` (simulates PackageKit being absent, so the both-backends-absent exit-9 path is testable), `FEZ_FAKE_PK_PLAN` (`protected` adds `systemd` to the PackageKit removal plan so the guardrail fires), and `FEZ_FAKE_PK_ERROR` (`notauth` injects a PackageKit `NOT_AUTHORIZED` error, mapped to exit 11).

## Conventions

- Error handling: `thiserror` enum + `pub type Result<T>`, propagate with `?`. No `anyhow`.
- Keep async/IO thin; put pure logic in sync helpers. Unit tests inline in `#[cfg(test)] mod tests`.
- `--json` output everywhere uses the `fez/v1` envelope; CLI serialization and bridge request bodies have different `None`/default semantics, so test them separately.
- CLI is self-documenting and stays usable by an LLM the way `git`/`gh` are. The capability registry in `src/capability/mod.rs` is **canonical**: `src/capability/help.rs::inject()` walks the derived clap tree and attaches each descriptor's `long`/`examples` as `long_about`/`after_help`, so `--help`, `fez describe`, `fez man`, and (indirectly) completions all derive from it. When you add or change a command, flag, or arg, update its clap `about` **and** the matching descriptor (summary, long, flags, examples) in the same change. Both `fez describe <id>` forms render from the same descriptor: `--json` serializes it whole, and the plain-text form goes through `Descriptor::render_text` (`src/capability/mod.rs`), which prints summary/long plus `privileged`, `output`, `inputs`, `flags`, and `examples` so text output carries the same actionable metadata as JSON (issue #62). The `services <action> <-> services.<action>` path/id mapping and the example wiring are locked by drift-guard tests in `tests/cli.rs`. `fez guide` renders the exit-code contract from `src/error.rs::EXIT_CODES` (one table, cross-checked against `exit_code()` by a test). The global `--force` help text is intentionally generic ("Override command-specific safety guardrails. See command help for exact risks."); the precise per-command risk wording (protected units, dangerous transactions, firewall lockout) lives in each descriptor's `long` (issue #63). `--dry-run` and `--force` are clap globals (`global = true` on the root `Cli`), so clap offers them on every subcommand; `inject()` hides them from a leaf's `--help` (and completions) when the descriptor's `flags` does not advertise them, so read-only command help mirrors its descriptor exactly (issue #61). The hide is help-only: a hidden global still parses (e.g. `fez network list --force` is accepted as a no-op, not a usage error), preserving the global contract. The mechanism is a local hidden non-global shadow arg with the same id, because clap propagates globals lazily and they cannot be reached via `mut_arg` on the child. A `help_flags_match_descriptor_flags` drift-guard test in `tests/cli.rs` asserts each leaf's safety-global visibility matches its descriptor.

## Notes

- The `packages` capability drives **dnf5daemon** (`org.rpm.dnf.v0`) over the bridge. The target must have the daemon installed and activatable. The package that provides the `org.rpm.dnf.v0` D-Bus service is **`dnf5daemon-server`** (not `dnf5daemon`, which does not exist as a package name); the remediation string in `dependency_missing()` and the install command must use `dnf5daemon-server`. When it is absent, fez returns exit 9 (`dependency-missing`) with remediation in the envelope `detail`. **Availability is OS-dependent: Fedora 41+ ships `dnf5daemon-server`; RHEL 10 does NOT.** RHEL 10 keeps dnf4 as the system manager and the dnf5/dnf5daemon stack targets RHEL 11 (upstream dnf5 PR #780 blocks dnf5 from replacing dnf on RHEL 10), so the package is absent from BaseOS/AppStream and not a repo-enable away. **When dnf5daemon is absent, `packages` no longer fails: it transparently falls back to the PackageKit backend (see the next note).** Only when *both* dnf5daemon and PackageKit are absent does it return exit 9 (the remediation then names both daemons). (issue #50)
- The `packages` capability falls back to **PackageKit** (`org.freedesktop.PackageKit`) when dnf5daemon is absent (notably RHEL 10), implemented in `capabilities/packages_pk.rs`. The fallback is automatic and self-configuring: `open_session` reports `DependencyMissing` on the dnf5daemon `ServiceUnknown`, and `run_read`/`run_mutation` then delegate to `packages_pk` (no `--backend` flag or env knob). PackageKit is signal-driven (per-transaction `CreateTransaction` -> method -> `Package`/`Finished` signals collected via `BridgeClient::dbus_call_collect`), so the request/reply `dbus_call` path is untouched. Reads (`list`/`info`/`search`/`check-update`/`repolist`) run unprivileged; mutations (`install`/`remove`/`upgrade`) open a **privileged** channel because PackageKit's mutation polkit actions are all `auth_admin` (no passwordless path for a normal user) and only a root caller (cockpit escalates the bridge to root) bypasses that check, so escalation behaves uniformly with dnf5daemon (a no-escalation host gets exit 11). PackageKit's plan carries **no install/download sizes** (only `info`/`package_id`/`summary` per package), so PackageKit payloads set size fields to `null` and carry `"backend":"packagekit"` plus a degraded-schema hint; dnf5daemon payloads carry `"backend":"dnf5daemon"`. The removal guardrail (`safety::check_removal_plan`) and audit flow are reused unchanged (a protected removal is exit 10, `dangerous-transaction`). A PackageKit `NOT_AUTHORIZED` error maps to exit 11 (`access-denied`). The e2e matrix's RHEL 10 `packages skip` should be revisited to exercise the PackageKit path now that it works (follow-up).
- The `firewall` capability drives **firewalld** (`org.fedoraproject.FirewallD1`) over the bridge. Interface discipline matters: runtime zone reads (`getZones`/`getServices`/`getPorts`/`getInterfaces`/`getSources`) go on `org.fedoraproject.FirewallD1.zone`, while `getDefaultZone`/`listServices`/`queryPanicMode` and mutations go on the root `org.fedoraproject.FirewallD1`; calling a method on the wrong interface is a real-firewalld `UnknownMethod` (the original cause of issue #33, where `getZones` was wrongly sent to the root interface). `list`/`show`/`services` are fully unprivileged. `status` is **mostly** unprivileged but escalates for one thing: the permanent-config read it does to compute runtime-vs-permanent drift. firewalld classifies permanent `config`/`config.zone` reads under `PK_ACTION_CONFIG` (`auth_admin_keep` on server **and** desktop installs), so that read must arrive on a privileged channel; `status` opens a second, privileged channel just for it (issue #34). A host with no escalation mechanism therefore fails `status` with exit 11 rather than silently reporting empty drift. Mutations (add/remove service/port, set-default-zone, reload, confirm, panic, masquerade) escalate. fez holds no state: mutations apply to **runtime only** and persistence happens exclusively via `fez firewall confirm` (firewalld's `runtimeToPermanent`); `status` recomputes drift live each call. A pure protected-op guard in `safety.rs` refuses lockout-prone ops (removing the session ssh service/port, any default-zone change, `panic on`, a drift-discarding `reload`, and disabling masquerade) without `--force` (exit 8); enabling masquerade is unguarded, disabling is protected (exit 8). When firewalld is absent, fez returns exit 9 (`dependency-missing`); the package to install is `firewalld`. firewalld is D-Bus-activated, so an absent service and a stopped-but-installed one are not observably distinct over the bridge (both surface as the name being unreachable: `ServiceUnknown`/`NameHasNoOwner`, or cockpit closing the channel `not-found`/`not-supported`). `map_fw_error` (`capabilities/firewall.rs`) therefore collapses all of those to `dependency-missing` (exit 9), whose remediation covers **both** install and enable+start, rather than inventing a `service-inactive` code fez cannot reliably detect; the error envelope also carries read-only follow-up `hints` (`fez services status firewalld.service`). A `UnknownMethod` reply (an older firewalld lacking a method, e.g. `getMasquerade`) maps to `FezError::UnsupportedApi` (code `unsupported-api`, exit **12**) carrying the method name, so a caller treats the feature as unsupported instead of recommending an install (issue #60). Test-only fake knobs: `FEZ_FAKE_FIREWALLD_UNREACHABLE` (close the FirewallD1 channel `not-found`) and `FEZ_FAKE_NO_MASQUERADE` (return `UnknownMethod` for `getMasquerade`).
